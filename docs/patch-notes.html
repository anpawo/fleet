Corrigé Desktop.raise 3e2b41b

Cliquer une tuile ne faisait rien

Symptôme
Le clic sur une session dont la fenêtre vit sur un autre bureau ne menait nulle part. L'app passait au premier plan, et on restait sur place — donc devant une fenêtre de terminal quelconque, sans l'onglet Claude Code attendu.
Cause
Desktop.raise ne demandait que la fenêtre focalisée de l'instance hôte. Une instance dont l'unique fenêtre est sur un autre bureau n'en a aucune : AXFocusedWindow répond kAXErrorNoValue. Le poll tournait deux secondes à vide, puis abandonnait — exactement le cas pour lequel la levée existe.
Correctif
À défaut de fenêtre focalisée, prendre la première d'AXWindows. C'est celle que TerminalFocus vient de placer en tête de l'ordre de cette instance via Scripting Bridge : la bonne, pas seulement la disponible.
Mesure
--ax-probe 1646, sur le Terminal hôte de la session my-hub : 
AXWindows        err=0        count=1   → ✳ Photo — suppression…
AXFocusedWindow  err=-25212    kAXErrorNoValue
AXMainWindow     err=-25212
AXRaise(AXWindows[0])  → err=0   la fenêtre traverse le bureau
Corrigé TerminalLaunch 2f787fa

Le nouveau bureau s'ouvrait sans toi dedans

Symptôme
Le + créait bien le bureau et y ouvrait bien le terminal, mais on se retrouvait ramené sur le bureau précédent, la fenêtre neuve restée seule derrière.
Cause
L'AppleScript activait le terminal avant de créer la fenêtre. Activer une app qui n'a aucune fenêtre sur le bureau courant laisse un choix à macOS, et il prend celui que personne ne veut : il vous emmène vers un bureau qui en a déjà une.
Correctif
do script d'abord, activate ensuite — même ordre pour iTerm2. Il y a alors une fenêtre ici, donc plus de choix à faire.
Corrigé Desktop.swift · commentaires 3e2b41b

Un commentaire faux qui fabriquait le bug

Symptôme
Le fichier affirmait à deux endroits qu'AXWindows ne liste que les fenêtres du bureau actif. C'est cette croyance qui avait fait écrire le code de la levée sur la seule fenêtre focalisée.
Cause
C'est faux, et mesurable : AXWindows a listé la fenêtre d'un Terminal posé sur un autre bureau, titre lisible et AXRaise opérant.
Correctif
Les deux commentaires réécrits avec ce qui a été observé. Ce qu'AXWindows omet, ce sont les fenêtres des autres instances — pas les autres bureaux.

Ouvert macOS · window server

L'énumération des fenêtres s'est vidée pour toutes les apps

Symptôme
Pendant environ une heure le 18 août au soir, l'Accessibility API a renvoyé zéro fenêtre pour toutes les applications, Fleet compris. Plus aucune levée, plus aucun passage en plein écran. CGWindowList, lui, voyait tout.
Mesure
System Events → firefox : 0 fenêtres   (attributs lisibles, menu bar = 1)
System Events → Code    : 0 fenêtres
TextEdit tout neuf      : 1 fenêtre selon TextEdit, 0 selon AX
Suspect
Mon appel à SLSManagedDisplaySetCurrentSpace pendant la mesure des API privées, qui désynchronise la notion de bureau courant du window server. Non établi.
État
Revenu de lui-même, sans déconnexion. killall Dock et Ctrl-flèche n'avaient rien changé. Pas de reproduction, donc pas de correctif — et pas d'appel privé de ce genre dans le code livré.

Ouvert TCC · Fleet

Les titres de fenêtres remplacés par le nom de l'app

Symptôme
fleet --windows affiche Terminal, Firefox, Code au lieu des vrais titres.
Cause
macOS masque les titres de fenêtres aux processus sans autorisation d'enregistrement d'écran. La base TCC de l'utilisateur ne contient aucune entrée kTCCServiceScreenCapture pour com.mr.fleet.
État
Non corrigé, et sans effet sur les tuiles — leurs titres viennent des transcripts, pas des fenêtres. Seul le débogage en souffre. Correctif connu : accorder « Enregistrement de l'écran » à Fleet.
Ouvert Spaces · route « vrai Space »

Des bureaux vides laissés derrière

Symptôme

Ouvert Terminal.app

Six instances de Terminal tournent en parallèle

Symptôme
Six processus Terminal.app distincts, dont plusieurs sans aucune fenêtre.
Conséquence
Fleet s'en sort — il parcourt toutes les instances plutôt que la première. Mais tell process "Terminal" de System Events tombe sur une instance sans fenêtre, ce qui donne un faux négatif convaincant et m'a fait diagnostiquer une panne générale d'Accessibility qui n'en était pas une.
État
Origine non établie. Rien à corriger dans Fleet tant que la cause est dehors.
Ouvert TerminalLaunch · plein écran

La fenêtre naît ici avant de partir sur son bureau

Symptôme
Le + ouvre la fenêtre sur le bureau courant, puis la passe en plein écran — on voit donc le terminal apparaître ici une fraction de seconde avant l'animation.
État
Inhérent à la seule route API disponible : c'est le plein écran qui fabrique le bureau, et il faut une fenêtre pour le demander. Ni contournable ni grave, mais visible.

Mesure

Mission Control · barre des Spaces

Les vignettes de bureaux n'ont pas d'identifiant

Mesure
Sous mc.spaces.list, chaque bureau est un AXButton sans AXIdentifier, au titre localisé (Bureau 7), avec les actions AXPress et AXRemoveDesktop. Les groupes au-dessus (mc, mc.display, mc.spaces) en ont un.
Lecture
Un nouveau bureau ne peut donc être désigné que par sa position — le dernier, une fois le compte augmenté. C'est tenable, mais c'est la pièce qu'une mise à jour de macOS déplacera en premier.
