Corrigé TerminalWatch.read 60adf8d

Un tour long pris pour une question

Symptôme
alt-tab en NEEDS YOU pendant dix minutes, sans rien demander. Sur son écran : ✶ Slithering… (9m 59s · ↓ 4.8k tokens) — le modèle écrivait.
Cause
Le même angle mort que l'erreur d'API, sous un autre visage. Un tour qui met des minutes à dire quoi que ce soit — un long bloc de réflexion, un flux lent — n'écrit rien dans le transcript tant que le message n'a pas atterri, ne brûle pas de CPU pendant qu'il attend le réseau, et ne tire aucun hook. Silence et tour dû : la signature exacte d'une question posée à l'écran.
Correctif
La lecture d'écran répond maintenant en trois temps au lieu de deux : en train de réessayer, en train de travailler, ou rien à ajouter. Le spinner est reconnu à son compteur de tokens, pas au mot qui le précède — ce mot change à chaque fois, exprès. Le troisième cas est celui qui compte : il laisse le bleu en place, donc une vraie question reste bleue.
Mesure
alt-tab     spinner à l'écran           →  working   NEEDS YOU → WORKING
my-hub      spinner à l'écran           →  working
video-code  posé sur son prompt, vide   →  unknown   la couleur devinée est gardée
Corrigé TerminalWatch 1e39c05

Une erreur d'API qui réclamait ton attention

Symptôme
fleet et alt-tab en NEEDS YOU alors qu'aucune des deux ne demandait quoi que ce soit : en bas de leur terminal, API error · Retrying in 0s · attempt 1/10.
Cause
La suite directe du correctif ci-dessous. Une requête qui échoue n'écrit rien : pas une entrée de transcript, pas un hook, pas de CPU. Le tour reste dû, le fichier ne bouge plus — exactement la signature d'une question posée à l'écran, que l'heuristique lit en bleu au bout de 25 s. Les dix tentatives avec backoff dépassent les trois minutes au bout desquelles le hook « running » cesse d'être cru, donc le bleu finit toujours par tomber.
Correctif
Le seul témoin est l'écran. Fleet parle déjà à l'onglet par son tty pour le remonter au premier plan ; il lui demande maintenant ce qu'il affiche — mais uniquement pour une session qui a déjà l'air de t'attendre, et seulement sur les huit dernières lignes, parce que Claude Code épingle son statut en bas de l'écran alors que le scrollback au-dessus peut très bien être une conversation au sujet des erreurs d'API. Ces sessions-là prennent une quatrième couleur, l'ambre, et ne comptent plus dans le « n of m need your input » ni dans les notifications.
Mesure
alt-tab  hook working 607 s   cpu 0.1 %   transcript muet
écran    ✻ API error · Retrying in 0s · attempt 1/10
tuile    NEEDS YOU  →  API ERROR
fleet    même écran cité en prose dans le scrollback  →  reste WORKING
Corrigé SessionRegistry.state b39469e

Une tuile restée rouge sur un tour mort

Symptôme
my-hub affichée WORKING pendant trente-cinq minutes, alors que la session était revenue à son prompt, écran vide, processus endormi.
Cause
Le hook UserPromptSubmit écrit « running » au départ du tour. Si la requête meurt là — limite d'usage, connexion coupée — Claude Code n'écrit pas une ligne dans le transcript et ne tire aucun hook de fermeture. Or Fleet donnait raison au hook tant que le transcript n'avait pas parlé après lui : ni l'un ni l'autre n'ayant bougé, le rouge était gelé pour toute la vie de la session.
Correctif
Un hook « running » cesse d'être cru au bout de trois minutes sans rien : aucun outil en vol, aucune écriture, aucun CPU. L'heuristique du transcript reprend alors la main — elle sait lire un tour dû resté muet et le dit en bleu, « va voir ». Le seuil est très au-dessus de celui de l'heuristique (25 s) : il ne s'agit pas d'arbitrer une supposition mais de contredire Claude Code lui-même.
Mesure
transcript figé à 03:28:09, dernière ligne = le prompt lui-même
hook           working, 2116 s   cpu 0.0 %   aucun outil en attente
tuile          WORKING  →  NEEDS YOU
Corrigé Desktop.raise 3e2b41b

Cliquer une tuile ne faisait rien

Symptôme
Le clic sur une session dont la fenêtre vit sur un autre bureau ne menait nulle part. L'app passait au premier plan, et on restait sur place — donc devant une fenêtre de terminal quelconque, sans l'onglet Claude Code attendu.
Cause
Desktop.raise ne demandait que la fenêtre focalisée de l'instance hôte. Une instance dont l'unique fenêtre est sur un autre bureau n'en a aucune : AXFocusedWindow répond kAXErrorNoValue. Le poll tournait deux secondes à vide, puis abandonnait — exactement le cas pour lequel la levée existe.
Correctif
À défaut de fenêtre focalisée, prendre la première d'AXWindows. C'est celle que TerminalFocus vient de placer en tête de l'ordre de cette instance via Scripting Bridge : la bonne, pas seulement la disponible.
Mesure
--ax-probe 1646, sur le Terminal hôte de la session my-hub : 
AXWindows        err=0        count=1   → ✳ Photo — suppression…
AXFocusedWindow  err=-25212    kAXErrorNoValue
AXMainWindow     err=-25212
AXRaise(AXWindows[0])  → err=0   la fenêtre traverse le bureau
Corrigé TerminalLaunch 2f787fa

Le nouveau bureau s'ouvrait sans toi dedans

Symptôme
Le + créait bien le bureau et y ouvrait bien le terminal, mais on se retrouvait ramené sur le bureau précédent, la fenêtre neuve restée seule derrière.
Cause
L'AppleScript activait le terminal avant de créer la fenêtre. Activer une app qui n'a aucune fenêtre sur le bureau courant laisse un choix à macOS, et il prend celui que personne ne veut : il vous emmène vers un bureau qui en a déjà une.
Correctif
do script d'abord, activate ensuite — même ordre pour iTerm2. Il y a alors une fenêtre ici, donc plus de choix à faire.
Corrigé Desktop.swift · commentaires 3e2b41b

Un commentaire faux qui fabriquait le bug

Symptôme
Le fichier affirmait à deux endroits qu'AXWindows ne liste que les fenêtres du bureau actif. C'est cette croyance qui avait fait écrire le code de la levée sur la seule fenêtre focalisée.
Cause
C'est faux, et mesurable : AXWindows a listé la fenêtre d'un Terminal posé sur un autre bureau, titre lisible et AXRaise opérant.
Correctif
Les deux commentaires réécrits avec ce qui a été observé. Ce qu'AXWindows omet, ce sont les fenêtres des autres instances — pas les autres bureaux.

Ouvert SessionRegistry · états

Un tour mort et un tour en attente de quota se ressemblent

Symptôme
Les deux produisent exactement la même trace : un prompt écrit, puis plus rien — pas d'écriture, pas de CPU, pas de hook. Fleet les lit désormais tous les deux en bleu au bout de trois minutes.
Conséquence
Bleu est juste pour un tour mort, qu'il faut relancer à la main. Il est trompeur pour un tour qui repartira seul quand le quota se libère : rien ne vous attend, il n'y a qu'à patienter.
État
Non résolu : il faudrait que Claude Code distingue les deux — un hook, une ligne de transcript, quoi que ce soit. Rien de tel n'a été trouvé côté hooks (UserPromptSubmit, PreToolUse, PostToolUse, Notification, Stop).

Ouvert TCC · Fleet

Les titres de fenêtres remplacés par le nom de l'app

Symptôme
fleet --windows affiche Terminal, Firefox, Code au lieu des vrais titres.
Cause
macOS masque les titres de fenêtres aux processus sans autorisation d'enregistrement d'écran. La base TCC de l'utilisateur ne contient aucune entrée kTCCServiceScreenCapture pour com.mr.fleet.
État
Non corrigé, et sans effet sur les tuiles — leurs titres viennent des transcripts, pas des fenêtres. Seul le débogage en souffre. Correctif connu : accorder « Enregistrement de l'écran » à Fleet.

Mission Control · barre des Spaces

Les vignettes de bureaux n'ont pas d'identifiant

Mesure
Sous mc.spaces.list, chaque bureau est un AXButton sans AXIdentifier, au titre localisé (Bureau 7), avec les actions AXPress et AXRemoveDesktop. Les groupes au-dessus (mc, mc.display, mc.spaces) en ont un.
Lecture
Un nouveau bureau ne peut donc être désigné que par sa position — le dernier, une fois le compte augmenté. C'est tenable, mais c'est la pièce qu'une mise à jour de macOS déplacera en premier.
